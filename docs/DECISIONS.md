# Decisions

## Assumptions

- Server layout and tooling follow `docs/ARCHITECTURE.md`. The decisions below settle what it left open.
- Setup issues come before feature issues, so `server/` has a health endpoint only. The config loader validates every setting `.env.example` lists, because Docker and the later providers need them.
- The server runs TypeScript directly with `tsx` instead of a compile step: one less build stage for a small app. Revisit if start-up time or image size matters.
- Docker Compose reads `.env.example` directly so `docker compose up` works with no setup. A `.env` file overrides it.
- In Docker the client is served by nginx, which proxies `/api` to the server. The browser sees one origin; `CLIENT_ORIGIN` still sets the server's CORS allow-list.
- Mailpit is the default mail catcher: free, no signup, has a web UI.
- Work is on branch `setup/foundation` rather than the stale `feature` branch from `git-workflow.md`.
- Contract conflict: Fake Store field names are mapped inside the `fakestore` adapter. The API returns `Product`. `GET /products/:id` adds an optional `description`, so the product page can show full details; the list endpoints omit it. `design-system/contract.md` needs that one optional field.
- Routing uses `react-router`: four pages, and hand-rolled routing is more code than the dependency.
- "Top rated" is the top 3 by rating per category, a constant in the catalogue service. The brief gives no number.
- No caching in the PoC. Add an in-memory TTL cache inside the provider only if latency hurts.
- The interfaces are `ProductProvider` and `Mailer`, as in the rules. Agent and skill files were renamed to match.
- Fake Store requests time out after 5 seconds, a constant in the adapter.
- A 404 or an empty body from Fake Store means "not found", and `get by id` returns `null`. Other non-2xx, timeouts and invalid JSON become `UpstreamError`.
- Upstream data is validated all-or-nothing: one malformed product fails the whole list with `UpstreamError`, rather than silently dropping it.
- Fake Store ids are numbers; the adapter maps them to string ids in our `Product`.
- The pagination and top-rated response shapes in `client/src/lib/api.ts` follow `docs/ARCHITECTURE.md`. They are checked against the server by contract tests (see the #8 contract entry).
- The provider factory is not wired into `server/src/index.ts` until the first service issue needs it.
- The adapter builds the upstream URL from the id, so the route-level id schema must reject `.` and `..`, for example `^[\w-]+$`.
- Node 22 or newer is required (jsdom 31); Node 20 breaks the client jsdom tests. CI runs the suites on Node 22 and they pass; they were also run locally on Node 24. Local `node` may resolve to v20 via nvm in both Git Bash and PowerShell: put `C:\Program Files\nodejs` first on PATH and check `node -v` before debugging.
- Featured list: `FEATURED_PRODUCT_IDS` is a comma-separated string of ids, split and trimmed once in config. It is required with no code default (fail fast; the list is config, not code). `.env.example` ships `1,2,3,4,5`. Changing it needs a restart only.
- The count is not enforced: the endpoint returns whatever is configured, so "exactly five" in `.env.example` and `ARCHITECTURE.md` is a guideline, not a startup check. Blank entries are ignored. An empty list shows the empty state.
- `react-router` is justified: it routes home, category, search and product pages.
- Resolved in #6: home cards and `Enquire` now open the product page. `NotFoundPage` remains as the `*` catch-all.
- CORS has no preflight handling yet; it is added with the enquiry POST (#7).
- The server error handler logs `req.path` only. It must never log the enquiry body.
- Unknown `/api` paths return a JSON 404.
- Featured order is the configured order, not upstream order.
- A configured id the provider cannot find is skipped and logged. Other upstream failures (`UpstreamError`) fail the request, as for every endpoint. Reason: one stale id should not blank the home page.
- Featured cards link to `/products/:id`, the product page route.
- Featured empty state (no ids configured, or none found) reads "No featured products right now. Try browsing a category."
- SUPERSEDED by #8 (see the Pagination entries below): Category page (#4) keeps the `{ topRated, products, page, pageSize, total }` shape but did not page: it returned every non-top-rated product with `page: 1`, `pageSize` equal to `products.length`, and `total` the count of `products`. `page` and `pageSize` were not read. Still true: `total` counts `products` only, not `topRated`.
- Ranking: rating descending, a missing rating sorts last, ties break by id ascending (numeric-aware string compare), so the order is stable. `topRated` is the first 3 of that order and `products` is the remainder in the same order, so no product appears twice. A category with 3 or fewer products has an empty `products` list.
- Category names are matched exactly and case-sensitively against `provider.listCategories()`, with no normalising. The client sends them with `encodeURIComponent` (for example `men's%20clothing`); Express decodes the path param.
- Unknown category: the service checks the name against `listCategories()` and throws `NotFoundError` (404). A known category with no products returns 200 with empty lists. Costs one extra upstream call; no caching, per the existing decision.
- Category names stay raw in the API. The UI uppercases the first letter only (CSS `first-letter:uppercase`; never title case, per the design README); no label mapping, and upstream spellings such as "jewelery" are not corrected.
- Category links appear in the site header nav (every page) and as a "Browse categories" list on home, from one shared component that reads `GET /categories`.
- Category page copy: empty reads "No products in this category yet. Try another category."; unknown reads "We could not find that category. Choose one from the menu."; the "Top rated" section heading shows only when `topRated` is not empty, and "More in this category" only when `products` is not empty.

NEW SERVER DEPENDENCIES, APPROVED BY THE USER: `nodemailer` (runtime) and `@types/nodemailer` (dev, because `code-style.md` forbids `any` and nodemailer ships no types). `CLAUDE.md` says no new libraries without asking; the user approved both. - Pagination (#8) supersedes the #4 and #5 "ignored until #8" entries: both list endpoints now read `page` and `pageSize`. `GET /products/featured` and `GET /categories` stay unpaginated. PRODUCT.md says pagination is not needed at ~20 products; it is built for future proofing only.
- Pagination (#8): defaults `page=1`, `pageSize=12`; `page` is an integer >= 1, `pageSize` an integer 1-50. A missing param takes the default. A non-integer or out-of-range value is `400 validation_failed` with `fields.page` or `fields.pageSize` (the shared shape), not clamped: silent clamping hides client bugs. The schema is a strict digit string (`/^\d+$/`, then number, integer, range), not `z.coerce.number()`, so `1e1`, `0x10`, `1.0`, empty and a repeated param (`?page=1&page=2`, an array) are all 400; coerce would accept the first three and turn `['1']` into 1. The schema lives in `routes/schemas.ts` and is used by both list routes. On search, `q` and pagination errors are merged into one `fields` object (one 400, not first-error-wins). The client sanitises `?page=` itself with `parsePage` (digits only; anything else, or a value too large, becomes 1; '007' becomes 7), so a hand-edited URL never shows a 400. The client does not send `pageSize` and uses the server default. `page` is capped at 1,000,000 so the offset arithmetic `(page - 1) * pageSize` stays exact (a `MAX_SAFE_INTEGER` cap would allow inexact offsets); the failure message is 'Use a whole number from 1 to 1000000.' (and 'Use a whole number from 1 to 50.' for `pageSize`). Validation runs before any lookup: bad paging is `400` even for an unknown category, and tests pin that order.
- Pagination (#8): a page past the end is `200` with an empty list and the real `total`, never an error. The pages show "That page does not exist." with a "Go to the first page" link (no clamping or redirect), and tell it apart from a genuinely empty result by `page > 1 && products.length === 0`. This is a UI inference, accepted. Review fix: the first draft used `total > 0`, which fails for a category with 3 or fewer products (`total` is 0, `topRated` is `[]` on page 2+), so `?page=2` would wrongly read "No products in this category yet". Page 1 with nothing to show stays the empty state. An unknown category is still a 404 on any page (the category check runs before paging).
- Pagination (#8): slicing lives in the catalogue service (one `paginate(items, page, pageSize)` helper), so it works with any provider. Routes only parse and shape. The service returns `page`, `pageSize` and `total` along with the items, so routes only apply `toCard`. The response echoes the requested `page` and `pageSize` (not `products.length`). `total` is the match count on search and the count of `products` (excluding `topRated`) on a category.
- Pagination (#8): on a category, `topRated` (first 3 by rating) is returned only on page 1 and is `[]` on page 2+; only the remainder `products` is paged. Reason: repeating the top 3 on every page is noise, and the server decides it, so the client has no rule. Search keeps provider order, as before.
- Pagination (#8): the client derives `totalPages = max(1, ceil(total / pageSize))`. That is arithmetic, not a business rule.
- Pagination (#8): URL state is `/categories/:category?page=N` and `/search?q=..&page=N`; page 1 omits the param. Back, forward and reload work because the URL is the state. A new search or category link carries no `page`, so it resets to 1. Each page is keyed by `category|term` plus `page`, so a page change remounts and shows loading, as the pages already do for a new term.
- Pagination (#8): one shared `Pagination` component (existing `Button` as a router link, no new library). It renders nothing when `totalPages <= 1`; otherwise a `nav` labelled "Pagination" with "Previous", "Page X of Y" and "Next". Previous is disabled on page 1 and Next on the last page. Ruling: a disabled control is a real `<button disabled>` (not a link with `aria-disabled`): it is out of the tab order, cannot be clicked, is announced as unavailable, and takes the design-system disabled look from `Button`. It is kept rather than removed so the layout does not jump. An enabled control is `Button asChild` around a react-router `Link`, so it is a real link. Props are `page`, `pageSize`, `total` and `to(page): string`; the callers own the URL shape.
- Pagination (#8): after a page change the link navigates with `state: { paged: true }` and the page focuses its `h1` (`tabIndex={-1}`) and scrolls to the top. Without this the clicked link unmounts and keyboard focus is lost. Focusing the heading is what announces the change; no `aria-live` region. Direct loads and reloads do not move focus. The focus-and-scroll code is one small hook, `lib/usePagedFocus.ts`, used by the two pages, so the `{ paged: true }` state shape has one home. The hook clears the history state after use (`navigate` with `replace` and state `null`), so a reload, or Back or Forward to an entry reached via Next, does not re-focus the heading. Review fix: it first left `{ paged: true }` in history. Verified in a memory router only, not in a real browser.
- Pagination (#8): each page request refetches the full list upstream (no cache). Fine at about 20 products; a short TTL cache in the service is the upgrade path.
- Pagination (#8): "Go to the first page" is a secondary `Button` (a design-reviewer fix; it was built primary). The pager wraps (`flex-wrap`, row gap) at large text sizes. The 320px single-row fit is ESTIMATED at about 266px of 288px and NOT verified in a browser; someone should check it once.
- Pagination (#8): the `ProductPage` test "opens from a category card" is a deliberate cross-page test. The exported interface was renamed `ProductListPage` because `ProductPage` collided with the component.
- Pagination (#8): the paging response shapes are checked by contract tests on both sides (server `catalogue.contract.test.ts`, client `paging.contract.test.tsx`). The contract JSON is copied by hand into both, so it can drift; a shared fixture file is the upgrade path, as for #7.
- Pagination (#8) is the nice-to-have: if the time-box is at risk, cut it first. The server code is small (a `paginate` helper and two schemas) and the UI is one component; with it cut, both endpoints keep returning everything with `page: 1`, as #4 and #5 shipped.

## Dropped or simplified

- Design system is consumed as stock shadcn components in `client/src/components/ui` with tokens in `client/src/index.css`, not as a separate package. Fewer moving parts for one app.
- The "no raw colours" rule is a small script (`scripts/check-boundaries.mjs`), not an ESLint plugin: the client lints with oxlint, which has no rule for this. The same script also covers the Fake Store host, `server/` imports and `fetch(` outside `lib/api.ts` checks.
- `client/src/lib/api.ts` now exists and is the only place `fetch(` may appear.

## Growth path

- Add providers behind `ProductProvider` and `Mailer` interfaces in `server/src/providers`; select them by config.
- Add a build step for the server image (compile to JavaScript) when image size matters.
- Multiple instances behind a load balancer need a shared rate-limit store, because the limiter is in memory per process.
- AWS: the plain Dockerfiles and env-only config run on ECS or App Runner; swap Mailpit for SES through a new `Mailer` adapter.

## Dependencies (#9)

- `shadcn` is a runtime dependency of the client only because `client/src/index.css` has `@import "shadcn/tailwind.css"`, the stock shadcn theme layer the components rely on.
- `tw-animate-css` was removed: nothing used it, and the project forbids animation.
- `toggle.tsx` and `toggle-group.tsx` are stock shadcn primitives listed in the design-system README. No page uses them now. They are kept as part of the supplied design system, and their lint warning is accepted.
- Server `@types/node` is aligned to `^22`, matching the Node 22 Dockerfile and CI.

## Logging (#9)

- The server error handler logs `ValidationError` and `NotFoundError` as one `warn` line (method, path, status, field names only). Stack traces are kept for upstream, mail and unexpected failures. Before this, routine 400 and 404 responses logged stacks at error level; a real docker run showed it.
